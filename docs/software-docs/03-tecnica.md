## Componentes
public/: interfaz, perfiles, geometría, edición y exportación. Three.js aporta representación 3D; clipper-lib realiza operaciones planares. El trabajo geométrico pesado dispone de worker y se prepara una representación de edición. build.js usa esbuild y genera docs/ y dist/. scripts/build-fr.mjs genera el estudio de escritorio completo en dist/fr; el acceso público /fr/ redirige al diseñador de clientes.
desktop-fr/: Electron, protocolo local, verificador Ed25519, pantalla de licencia, preload limitado y empaquetado. Node está deshabilitado en el renderer; el proceso principal valida licencias y controla descargas e impresión según capacidades. Los datos y proyectos quedan locales salvo una acción explícita del usuario.
commercial/: servicio HTTP Node 24 con SQLite WAL, portales de archivos/recuperación, webhooks, bandeja de correos y publicación. No requiere dependencias npm adicionales. La clave privada y la base de datos se configuran con rutas absolutas fuera del repositorio. Nunca se incluyen en el instalador.
## Compilación reproducible
Entorno de desarrollo recomendado: Node 24, npm, herramientas del sistema del empaquetador y SDK de firma correspondientes. Ejecutar npm ci, npm test, npm run build; después npm ci --prefix desktop-fr y node desktop-fr/stage.mjs. En .desktop-build ejecutar npm ci y el comando package:win, package:linux o package:mac. Estos comandos base generan candidatos internos SIN firma; no son el flujo comercial.
Para distribución use .github/workflows/commercial-signed.yml. Primero verifica configuración, compila, prueba y firma, comprueba identidad/notarización, prepara checksums firmados y publica únicamente si se solicitó almacenamiento externo. El flujo interno desktop.yml ya no publica automáticamente instaladores sin firma en Releases.
FR_LICENSING_API_URL se fija al compilar como origen HTTPS sin ruta, usuario ni parámetros. No contiene secreto. La clave pública de licencias se conserva en desktop-fr/license-public.pem; corresponde a la autoridad existente y no debe reemplazarse para solucionar un error de instalación. Firma de licencias y firma del ejecutable son autoridades distintas.
## Servicio y configuración
Copiar commercial/.env.example a un archivo privado fuera del repositorio. Configurar FR_ENV, FR_PUBLIC_BASE_URL, FR_SIGNING_KEY_FILE, FR_DATABASE_FILE, FR_VARIANTS_FILE y FR_VAULT_KEY. El vault requiere 32 bytes aleatorios en hexadecimal, guardados en un gestor de secretos. FR_ENV=production rechaza configuraciones ficticias, identificadores de productos incorrectos y claves privadas con permisos demasiado abiertos.
Arranque: node --env-file=/ruta/privada/fr.env commercial/server.mjs. Vinculación por defecto 127.0.0.1:8787; publicar detrás de TLS y un proxy que limite tamaño, tiempo y tasa. El Dockerfile usa Node 24, usuario sin privilegios y volúmenes externos para datos/secretos. Provisionar permisos de la carpeta persistente para el UID del contenedor.
No habilitar FR_TRUST_PROXY=1 salvo proxy local que reemplace X-Forwarded-For. Configurar firewall, HTTPS, rotación de logs sin claves/correos/cuerpos de webhooks, alertas de errores, monitorización y copias de seguridad cifradas. El límite en memoria no sustituye protección perimetral ni control de abuso distribuido.
## Protocolo de activación
POST /v1/activate recibe JSON con key y deviceId, y requestId opcional. deviceId es el identificador SHA-256 hexadecimal del equipo. La respuesta es un objeto con payload (cadena JSON exacta) y signature (Base64 Ed25519 sobre esa cadena). El cliente verifica firma, producto, equipo y vencimiento antes de guardar la licencia con permisos restrictivos.
El payload incluye product, licenseId, customer, deviceId, issuedAt, expiresAt, contractExpiresAt, licenseKind, plan, features y activationToken. La autorización dura como máximo 30 días y nunca supera el vencimiento contractual. El token de activación permite liberar ese puesto; una renovación genera un token nuevo. Las licencias legacy sin features mantienen capacidades completas por compatibilidad.
POST /v1/offline/activate usa la misma estructura desde el portal, con solicitud exportada del equipo offline. POST /v1/deactivate y /v1/offline/deactivate reciben key, deviceId, activationToken y requestId opcional; devuelven confirmación firmada action=deactivated. El cliente verifica licencia/equipo antes de retirar el archivo local. La solicitud offline contiene clave y debe transferirse por un canal privado.
POST /v1/recovery recibe email y responde genéricamente para no revelar compradores. Se genera un enlace de un uso válido 15 minutos y no se repite mientras haya uno pendiente. POST /v1/recovery/confirm recibe token y entrega la clave al usuario que posee el enlace. El portal elimina el token del historial visible antes de confirmarlo.
## Derechos, límites y revocación
Planes internos: perpetual, annual y enterprise. Los productos del proveedor se mapean a plan, puestos y features exclusivamente en configuración del servidor. Capacidades: edit, project, reference, patterns, glb, stl y team. El ejemplo incluye un producto básico sin exportación 3D. team describe el derecho contratado; no implementa todavía consola de gestión de usuarios ni SSO.
El cliente principal impide exportar/imprimir formatos no habilitados; la interfaz también deshabilita acciones. Esta implementación no constituye una solución antimanipulación de nivel comercial auditada. Deben evaluarse endurecimiento, SDK comercial y recuperación de reloj antes del lanzamiento.
No es posible revocar inmediatamente una autorización en un equipo desconectado. Un reembolso, transferencia o baja impide nuevas activaciones en servidor, pero la copia ya emitida puede funcionar hasta vencer su autorización, como máximo 30 días. La perpetuidad contractual y ese plazo de autorización deben indicarse antes de cobrar. Renovación por archivo evita exigir red permanente al equipo de diseño.
## Pagos y correo
Webhooks: POST /webhooks/lemonsqueezy y /webhooks/paddle. Validación HMAC sobre cuerpo original; Paddle valida también timestamp con tolerancia de cinco minutos. Los eventos se registran con identidad única y la emisión es transaccional. No se acepta un plan enviado por el navegador.
Lemon Squeezy: order_created, estado paid, tienda e ID de variante permitidos y coincidencia test/live. Paddle: transaction.completed, estado completed, price.id permitido; se consulta el email del customer_id mediante API de servidor. No se confía en un email de custom_data. Reembolso Lemon y ajuste Paddle aprobado de refund/chargeback revocan futuras activaciones del pedido.
La entrega implementada es compra de pago único, incluida licencia anual PREPAGADA. No se han implementado suscripciones recurrentes ni conciliación de renovaciones/cancelaciones. No configurar productos recurrentes hasta ampliar ese ciclo. Eventos repetidos no reemiten claves ni reactivan una licencia revocada.
Cada compra, primera activación y recuperación crea un correo en outbox cifrado. commercial/mail/templates.mjs contiene plantillas ES/EN. commercial/deliver-mail.mjs funciona por defecto en simulación y sólo informa cantidades; con MAIL_DELIVERY_ENABLED=true, remitente verificado y RESEND_API_KEY puede entregar usando idempotencia por mensaje. Hoy no existe esa cuenta y no se ha enviado correo real. Gmail actual sirve como soporte, no como dominio de envío empresarial verificado.
